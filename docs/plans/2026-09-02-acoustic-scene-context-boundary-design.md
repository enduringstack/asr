# 声音场景、上下文融合与定位权限边界设计

状态：提案，等待产品确认

日期：2026-09-02

适用工程：HarmonyOS 手机端 ASR Demo

## 1. 文档目的

本文回答四个问题：

1. 为什么当前工程的声音场景功能会涉及 Location Kit 和所谓“GNSS 速度”？
2. 这部分能力究竟属于声音模型，还是属于另一个系统级功能？
3. 它对精度、权限、隐私、功耗和 Demo 可信度有什么影响？
4. 工程后续应当保留、默认关闭，还是彻底移除定位逻辑？

本文只做方案审查，不在本阶段修改现有代码。最终建议是：**主 Demo 恢复为纯音频模型评测，移除生产路径中的定位权限和位置派生速度融合；如果以后确实要研究“系统级场景感知”，应作为独立实验功能重新立项、单独授权、单独采数和单独验收。**

## 2. 一句话解释当前实现

当前实现不是“声学模型需要 GNSS”，而是纯音频模型没有达到双 95% 后，为了尝试提高“地铁与高铁”的系统级判断准确率，引入 Location Kit 返回的速度作为额外规则证据。

这里有三个必须澄清的概念：

| 概念 | 实际含义 | 是否属于声音模型 |
|---|---|---|
| 纯音频场景识别 | 只根据麦克风音频判断地铁、高铁、商场、咖啡厅、音乐现场、其他 | 是 |
| Location Kit 速度 | 系统位置服务根据 GNSS、基站、WLAN/蓝牙等来源生成的位置结果中的速度字段 | 否 |
| 系统融合 | 把纯音频概率、位置派生速度、ASR 关键词和声音事件用规则重新加权 | 否，是产品级决策层 |

因此，之前将这项能力简称为“GNSS 融合”并不严谨。工程调用的是 HarmonyOS Location Kit 的融合定位接口，不保证数据只来自 GNSS。更准确的名称应当是“位置服务派生速度上下文”。

## 3. 背景与问题来源

声音场景六分类的目标为：地铁、高铁/城际列车、商场、咖啡厅/餐厅、音乐现场和其他。v4 来源隔离校准集上，当前最强的 Mac 教师特征融合实验准确率为 77.71%，宏召回率为 77.11%，没有达到准确率和宏召回率同时 95% 的发布门禁。

主要困难不是简单的模型大小或推理速度，而是场景在声学上真实重叠：

- 地铁、高铁、普通列车和公交车厢都可能包含稳定低频噪声、轨道/路面冲击、空调声和人声。
- 商场与咖啡厅都可能包含室内混响、人群、背景音乐和广播。
- “其他”是开放集合，包含机场、道路、办公室、公园、普通列车等大量未知分布。
- 高铁进站、停站或低速运行时，速度本身也不是“高铁”的充分证据。

作为难度参照，DCASE 2025 低复杂度声学场景挑战在严格未知设备条件下的官方最佳准确率约为 61.5%。这不代表本项目只能达到该数字，但说明开放域、跨设备的纯音频场景分类并不是靠增加一个小模型就能普遍达到 95% 的成熟问题。

位置派生速度正是在这个背景下加入的：如果音频在“地铁/高铁”之间摇摆，同时位置服务报告可靠的高速移动，则规则层增加高铁分数。但这改变了任务定义——结果不再是“声音模型效果”，而是“声音 + 传感器 + 文本 + 规则的系统效果”。

## 4. 当前代码的真实行为

当前实现由以下部分组成：

- `entry/src/main/ets/services/scene/SceneContextTracker.ets`
  - 使用 `@kit.LocationKit` 的 `geoLocationManager`。
  - 录音开始时订阅 `locationChange`，请求周期为 2 秒，场景为 `TRANSPORT`。
  - 从回调对象中读取 `speed`、`speedAccuracy` 和 `timeStamp`。
  - 内存最多保留 30 个速度样本，并计算速度中位数。
- `entry/src/main/ets/common/AcousticSceneFusion.ets`
  - 位置结果不超过 15 秒、速度精度不差于 20 km/h 时才视为可用。
  - 速度达到 120 km/h 时增加高铁分数，并降低地铁分数。
  - ASR 出现“高铁、动车、换乘、商场、咖啡、演唱会”等词语时增加对应场景分数。
  - 声音事件出现掌声、欢呼或餐具声时增加音乐现场或餐饮场景分数。
  - 所有权重都是人工规则，不是通过带同步传感器真值的数据训练或校准得到的。
- `entry/src/main/ets/pages/Index.ets`
  - 当前“上下文增强”默认打开。
  - 第一次录音时可能请求模糊位置权限。
  - UI 同时显示纯音频输出和融合输出。
- `entry/src/main/module.json5`
  - 声明 `ohos.permission.APPROXIMATELY_LOCATION`。

当前数据流如下：

```text
麦克风音频 ──┬── ASR ──────────────► 文本关键词 ─────┐
             ├── 声音事件模型 ──────► 事件标签 ───────┤
             └── 声学场景模型 ──────► 六类概率 ───────┼──► 人工规则融合 ─► 最终场景
                                                     │
Location Kit ─► 完整 Location 回调 ─► 仅取速度摘要 ───┘
```

必须准确描述隐私边界：代码没有把经纬度写入业务对象、数据库或日志，但 Location Kit 的回调对象本身包含位置结构，应用进程会先收到该对象，再由代码只挑选速度字段。因而不能宣传成“应用绝不会接收到位置”，只能说“业务逻辑不读取、不保存、不上传经纬度”。

## 5. 为什么这项能力不适合放在主 Demo

### 5.1 它破坏了单模型效果的可解释性

本 Demo 的核心价值是分别观察 ASR、标点、声纹、说话人分离、声音事件和声音场景模型的真实效果。如果场景卡片显示的是规则融合结果，用户无法判断：

- 是声音模型判断正确；
- 是 ASR 恰好说出了“下一站”；
- 是声音事件识别出掌声；
- 还是位置速度覆盖了声学模型。

即使 UI 同时展示两种结果，默认打开的融合仍会让“最终结果”显得比模型本身更可靠，容易造成指标口径混淆。

### 5.2 模糊位置权限与可靠速度存在矛盾

当前工程只申请 `APPROXIMATELY_LOCATION`。华为隐私保护文档说明，仅申请该权限时获得的是约 5 公里精度的模糊位置。Location Kit 可能融合 GNSS、基站、WLAN 和蓝牙等定位技术，但“模糊位置可用”不等价于“速度精度足以区分交通工具”。

当前代码虽然检查 `speedAccuracy`，仍缺少以下产品证据：

- 不同机型在模糊位置授权下是否稳定返回速度及速度精度；
- 地铁隧道、地下站和大型室内空间是否可用；
- 高铁进站、出站和停站期间是否会产生系统性漏判；
- 高速公路汽车、飞机滑行等高速“其他”是否会误判成高铁。

如果为了速度精度再申请精准位置权限，权限成本和用户疑虑会进一步上升，也偏离声音模型 Demo 的目的。

### 5.3 当前规则没有经过系统级训练或盲测

`120 km/h`、`15 秒`、`20 km/h` 以及各类加权值是合理启发式，但不是从带同步传感器标注的数据上拟合并冻结的参数。现有公开音频校准集没有同步位置、速度和现场 ASR 真值，所以无法证明融合准确率，更不能宣称系统达到 95%。

用文件名或真实标签人为生成“速度=168 km/h”只能测试代码分支，不能测量真实效果。若将这种单元测试结果包装成场景准确率，会产生数据泄漏。

### 5.4 权限、功耗和失败面不成比例

华为官方说明，位置能力需要用户主动开启位置开关并授权；业务结束时应用应主动停止请求。实时定位可能同时使用 GNSS 和网络定位，硬件资源和功耗开销高于纯音频推理。

主 Demo 因此额外引入：权限弹窗、位置总开关、室内无信号、系统功耗限制、机型差异、订阅生命周期、异常释放和隐私说明等失败面。对于一个只想试听声音模型效果的用户，这些复杂度没有形成经过验证的收益。

## 6. 三种方案对比

| 方案 | 说明 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 默认开启融合 | 录音时默认申请位置，融合速度、文本和事件 | 可能修正少量明显场景 | 权限突兀；指标混淆；没有真实系统评测 | 不采用 |
| B. 默认关闭、实验开关 | 主结果为纯音频，用户主动进入实验模式后授权 | 保留研究入口；对主流程影响较小 | 仍需维护权限和传感器代码；容易被误用 | 仅未来研究版可考虑 |
| C. 主工程移除定位融合 | 主 Demo 只展示各模型自己的输出 | 口径最清楚；无定位权限；最容易复现验收 | 无法借速度提高系统级结果 | **推荐** |

推荐方案 C。原因不是 Location Kit 没有价值，而是当前产品需求是“端侧语音与声音模型 Demo”，不是导航、交通方式识别或多传感器情境感知产品。遵循最小权限和 YAGNI 原则，未验证的定位依赖不应进入主路径。

## 7. 推荐目标架构

主工程应恢复为模型并列、相互独立的工作台：

```text
                                      ┌─► ASR 原始文本
                                      ├─► 标点后文本
录音 / 可播放数据集 ─► 音频预处理 ────┼─► 声纹注册与身份识别
                                      ├─► 说话人分离
                                      ├─► 声音事件 / 情绪 / 语言
                                      └─► 纯音频场景六类概率

每个模型卡片：输入范围 + 模型名 + 原始输出 + 置信度 + 耗时 + 真实标签（数据集模式）
```

架构规则如下：

1. 声音场景模型只消费音频特征，输出六类概率和窗口数。
2. ASR、声音事件和场景识别可以并行运行，但互不修改对方结果。
3. 数据集测试页只计算纯音频准确率、宏召回率、逐类召回率和混淆矩阵。
4. 录音页不请求位置权限，不展示速度，不出现“上下文增强”开关。
5. UI 不使用“最终场景”暗示多模型裁决，只写“声音场景模型输出”。
6. 如果将来重启多传感器研究，必须建立独立页面、独立开关、独立权限说明和独立指标；不能覆盖纯音频结果。

## 8. UI 信息架构建议

### 8.1 数据集模式

每条样本展示：

- 数据集、来源 ID、许可证和归属；
- 可播放的原始 30 秒音频；
- 真实场景标签；
- 声音场景模型输出；
- 六类原始概率、窗口数、耗时；
- 匹配/不匹配状态。

批量页展示准确率和逐类正确数。宏召回率必须在样本数足够且类别真值完整时计算。数据集模式不使用 ASR 文本、声音事件、定位或文件名辅助分类。

### 8.2 录音模式

声音场景卡片只显示：

```text
声音场景模型
高铁 / 城际列车        62.4%
分析窗口 3             端侧耗时 41 ms
提示：开放场景结果仅供参考
```

ASR、标点和声音事件放在各自卡片中，不把“下一站”或“掌声”偷偷注入场景概率。这样用户可以直接比较模型之间是否相互印证，但最终判断由用户完成。

### 8.3 未来实验模式（非本期）

如果未来确需系统融合，应单独命名为“多模态场景实验”，默认关闭，并按以下顺序交互：

1. 用户主动进入实验页；
2. 页面先解释为什么需要位置派生速度；
3. 用户单独授权；
4. 同时展示纯音频结果和系统融合结果；
5. 明确列出本次真正使用的证据；
6. 退出页面或录音结束立即停止定位。

## 9. 评测口径

### 9.1 纯音频模型指标

- 输入：仅音频波形或声学特征；
- 决策单位：同一原始录音的连续 30 秒；
- 数据隔离：按地点、原始录音、上传者或近重复组划分；
- 指标：准确率、宏召回率、逐类召回率、混淆矩阵、置信区间、RTF 和模型大小；
- 禁止项：ASR 文本、声音事件标签、位置、文件名和真实标签参与推理。

### 9.2 系统融合指标（未来）

必须重新采集带同步证据的手机实录：

- 原始音频；
- 人工确认的真实场景；
- 用户明确授权后的速度摘要和精度；
- 设备型号、室内/室外、地上/地下状态；
- ASR 和声音事件模型的真实运行输出；
- 不保存经纬度时，应在采集端立即丢弃坐标字段并留下可审计说明。

训练、校准和盲测要按完整行程或地点隔离。规则权重只能在训练/校准集选择，冻结后才能运行一次盲测。报告必须同时给出：纯音频指标、系统融合指标、拒绝授权子集指标、无定位子集指标和逐证据消融实验。

### 9.3 95% 门禁

“纯音频达到 95%”与“系统融合达到 95%”是两个不同声明，不能互换。任一声明都要求准确率和宏召回率同时达到 95%，并提供来源隔离盲测、样本量和置信区间。18 条 App 固定音频只能做可视化回归，不能证明 95%。

## 10. 隐私、安全与非功能要求

### 10.1 最小权限

- 推荐主 Demo 不声明任何位置权限。
- 麦克风权限只在用户主动录音时申请。
- 数据集播放与离线评测不请求麦克风和位置权限。
- 将来实验模式必须在进入功能后再请求位置权限，不能随首次录音顺带申请。

### 10.2 数据生命周期

- 纯音频模式不存在位置数据生命周期。
- 声纹向量继续按生物特征数据处理，与场景识别完全隔离。
- 如果未来恢复位置实验，速度摘要默认只驻留内存，录音结束立即清除；任何落盘或上传必须另行获得同意。

### 10.3 性能与功耗

- 纯音频场景模型端侧 RTF 门禁保持小于 0.25。
- 场景模型不得阻塞 ASR 实时回调和 UI 主线程。
- 移除 Location Kit 后，录音流程不再产生额外定位订阅和位置服务功耗。

### 10.4 可维护性

- 每个模型有独立输入、输出类型和测试数据。
- 不在页面组件中维护不可追溯的跨模型规则权重。
- 模型版本、输入采样率、Embedding/输出维度和阈值必须写入模型元数据。

## 11. 失败模式与处理

| 失败模式 | 当前融合路径影响 | 推荐纯音频路径处理 |
|---|---|---|
| 用户拒绝位置 | 融合自动退化，但用户已遇到无关权限弹窗 | 不请求位置，无此失败面 |
| 地铁隧道无定位 | 无速度，结果退化为音频/文本规则 | 纯音频正常运行并显示置信度 |
| 高铁停站 | 速度不足，无法获得高铁辅助证据 | 如实展示声学模型结果 |
| 高速汽车 | 可能因高速误增高铁概率 | 不使用速度，不产生该规则误判 |
| ASR 识别到广告中的“高铁” | 可能错误提升高铁概率 | ASR 与场景输出分开呈现 |
| 播放录音包含掌声 | 事件规则可能覆盖实际环境 | 声音事件和场景分别呈现 |
| 场景模型低置信度 | 融合可能制造更高的表面置信度 | 显示低置信度/其他，不隐藏不确定性 |

## 12. 代码调整范围（确认后实施）

如果本提案被接受，建议按一个小版本完成以下修改：

1. 从 `module.json5` 移除 `ohos.permission.APPROXIMATELY_LOCATION`。
2. 删除位置权限原因字符串。
3. 从 `Index.ets` 移除位置权限申请、`SceneContextTracker` 生命周期和“上下文增强”开关。
4. 场景结果直接使用原生声学模型的 `sceneClassIndex`、`sceneConfidence` 和 `sceneProbabilities`。
5. 移除主路径中的 ASR/声音事件场景加权；保留各模型独立输出。
6. 删除未再引用的 `SceneContextTracker.ets`、`AcousticSceneFusion.ets` 及对应融合测试，或将其移入明确不参与发布构建的研究目录。
7. 更新 UI 文案、隐私说明和评测报告。
8. 回归权限列表、61 项 ArkTS 测试、声学场景 Python 测试、HAP 打包和真机录音。

升级安装不得卸载 App 或清除用户数据。移除清单权限后，新版本不再申请和使用位置能力；发布验收还应检查系统设置中的应用权限展示是否符合预期。

## 13. 验收标准

本次边界修正完成的标准不是“场景准确率突然达到 95%”，而是：

- App 安装清单不包含位置权限；
- 首次和后续录音都不会弹出位置授权；
- 数据集与录音模式的场景结果只依赖音频；
- ASR、声音事件与场景输出互不修改；
- 18 条固定音频仍可播放并显示真实标签与六类概率；
- 纯音频评测结果与 Mac 同协议结果一致；
- ArkTS、Python、原生编译和 HAP 打包全部通过；
- 文档不再使用“GNSS 提升了模型精度”这类误导表述。
